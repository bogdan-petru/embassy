# One transfer, four responsibility layers

This example sends **Hello from DMA!** plus a newline: 16 bytes, once, from one
FRDM-MCXA577 to another. It is a new, small I2C controller, not a wrapper around
the full `controller::I2c`. The receiving board uses the existing Embassy DMA
target as a test peer and verifies the exact bytes and STOP.

There is now also a [short combined write/read](WRITE-READ.md): write one
register address, repeated START, read four bytes, STOP. Both use the same
four responsibilities; the receive extension adds exclusive buffer ownership.

Start with [the sending application](../src/bin/i2c-one-shot-controller.rs).
This version uses Abacus to generate state-specific `safe-mmio` accessors at
Rust compile time. See [the current integration](ABACUS-INTEGRATION.md),
[the former direct generator](DIRECT-SAFE-MMIO.md), and
[the original Abacus experiment](ABACUS-SAFE-MMIO.md);
[the broader design proposal](FRAMEWORK.md) remains only partially implemented.
The [implementation checkpoint](PROGRESS.md) keeps the historical baseline and
its evidence separate from the current source layout. Checkpoints 8 and 9 are
historical records for the former core/interface split and a runner-only RXSTALL
startup correction; their mutation and board outcomes remain tied to their
recorded commits. The current code completes a narrower L2/L3/L4 extraction:
the trusted physical capability is below a safe named-operation vocabulary, and
both that vocabulary and the typed protocol core forbid unsafe code. [Checkpoint
11](PROGRESS.md) records the direct generator replacement; checkpoint 10 retains
the completed evidence for the preceding boundary extraction. This is the
evidence and limits ledger for the layout;
this overview deliberately does not duplicate its aggregate mutation, HIL, or
CI results.

The [protocol properties](PROPERTIES.md) add generated sequences and an
independent model; the [scoped mutation check](CORE-MUTATIONS.md) tests whether
changed decisions are detected. Neither substitutes for MMIO or board evidence.
Dedicated [L3 Kani harnesses](../../../embassy-mcxa/experimental/i2c-one-shot-proofs/README.md)
now exercise the real vocabulary over an explicit modeled L2 binding, alongside
the existing L4 decision proofs. Their bounded scope and hardware assumptions
are recorded separately from the native tests and board results.

The next reuse step is now concrete: [reviewed Rust contracts](../../../embassy-mcxa/tools/driver-contracts/README.md)
check the Abacus access declarations for this I2C example and a separate
[UART DMA TX pilot](UART-PILOT.md). The UART pilot distinguishes DMA quiescence
from final wire completion. Protocol and physical cleanup hooks remain reviewed
code, not inferred from the PAC or generated from the natural-language contract.
The current [I2C porting guide](I2C-PORTING.md) explains its owned MCXA resource
binding and shared example/peer checks without changing those transfer rules.
The [lifecycle simplification](SIMPLIFICATION.md) records shared TX/RX cleanup,
one deadline wrapper, and the measured reduction without hiding shared code.
The subsequent [shared-control step](SHARED-CONTROL.md) generates private reset
I/O adapters and shares bounded polling, keeping the hardware recipes explicit.
Its accounting includes the additional shared/generated infrastructure.
The [representation simplification](REPRESENTATION-SIMPLIFICATION.md) removes
duplicate status/lease/result plumbing while retaining the opaque L2 boundary.

The part the application cares about is:

```rust
let port = McxaI2cPort::acquire(p.LPI2C3, p.P3_21, p.P3_20, p.DMA0_CH0, Irqs, ClockConfig::default()).unwrap();
let i2c = I2c::new(port).unwrap();
let message = TX.init(*b"Hello from DMA!\n");
i2c.write(0x2a, message).await.unwrap();
```

`TX` reserves static RAM once. `Irqs` is generated by Embassy's
`bind_interrupts!`: it proves that the selected I2C and DMA interrupt handlers
are installed. `.await` lets the executor run something else while hardware
works. DMA moves the bytes; the CPU still handles setup, START, STOP, and faults.

## Read in this order

| Architecture layer | File | What to notice |
| --- | --- | --- |
| L4. Core / transaction | [protocol.rs](../../../embassy-mcxa/experimental/i2c-one-shot-core/src/protocol.rs) and [session.rs](../../../embassy-mcxa/src/i2c/one_shot/session.rs) | Typed transfer sequence and fault priority; the HAL wrapper owns one deadline |
| L3. Named operations | [vocabulary crate](../../../embassy-mcxa/experimental/i2c-one-shot-vocabulary/) | Safe `Backend`; START/STOP composition over opaque capabilities and one shared decoded status type |
| L2. Trusted physical capability | [interface](../../../embassy-mcxa/experimental/i2c-one-shot-interface/) and [registers.rs](../../../embassy-mcxa/src/i2c/one_shot/session/vocabulary/registers.rs) | Sole unsafe `Device` contract, resource construction, ordered DMA arm/shutdown, IRQ wakes, and opaque CPU/TX/RX owners |
| L1. PAC | Cargo-pinned `nxp-pac` | Register offsets and bit/command encodings |

These are four responsibilities, not four runtime engines. The old
application/hardware-boundary/protocol-vocabulary reader numbering is retired:
the L1–L4 names above are now the architecture-note names used throughout this
experiment. The three small packages describe source boundaries for L2, L3, and
L4; they are not a fifth layer. The original write API and sequence remain;
`write_read` adds the separate, documented receive path.

Only L2's `Device` is an unsafe contract. The physical HAL implements it after
acquiring exclusive controller, DMA, clock, pin, and IRQ resources, then wraps
it in opaque `Cpu`/`InFlight` capabilities. L3's open `Backend` is safe: a mock
can lie about protocol facts, but it cannot extract a DMA channel, raw MMIO, or
in-flight lease from the real capabilities. Therefore a safe L3 sequencing
mistake can be a protocol bug without becoming a DMA-memory-safety escape.
The core and vocabulary both use `#![forbid(unsafe_code)]`; the interface has
only the declaration-only `unsafe Device` trait. The interrupt handler only
masks its NVIC vector and wakes the task; it never creates a second register
accessor.

The hardware boundary now returns `Off`/`Enabled` only after actual reset/enable
readback. Generated register writes alone cannot mint those states. DMA is
quiesced first; failed confirmation attempts to hold reset and stops rather than
returning authority. This is local-engine confirmation, not physical bus recovery.
The source rules do not reject a safe PAC call inside the trusted HAL, prove the
adapter correct, or make trusted dependencies unsafe-free.

## The whole transaction

The real implementation reads:

```rust
// idle owns the backend the HAL constructor built.
let started = idle.start(address)?;
let streaming = started.transmit(bytes)?;
let quiescent = streaming.drain().await?;
let stopping = quiescent.stop().await?;
stopping.complete().await
```

In plain English:

1. Queue START with the target address.
2. Connect the immutable source buffer to the controller's TX DMA request.
3. Wait until DMA has delivered all bytes to the peripheral and is quiescent.
4. Queue STOP after those bytes.
5. Wait for STOP and an idle controller before reporting success.

`StartQueued` means START **queued**, not address acknowledged. `TxDmaQuiescent`
means DMA finished feeding the peripheral, not that every byte was acknowledged on the
wire. Those distinctions matter: DMA completion alone is not I2C completion.
Every wait classifies faults as well as readiness.

`?` means “return this error immediately.” The hardware owner is still dropped
on that path; a programmer does not have to remember a separate cleanup call.

## The Layer-4 protocol is small and formal

The permitted sequence is:
`Idle -> StartQueued -> Streaming -> TxDmaQuiescent -> Stopping -> Result`.

For example, the actual state owner is:

```rust
pub struct TxDmaQuiescent<B: Backend>(B); // private backend field
```

These five owned states replace the earlier local transition macro. Advancing
consumes the old owner; only the protocol implementation can construct the next
one from the backend's observed outcome. A Pending DMA result retains the same
controller/channel/source lease. No detached, reusable evidence token escapes.
The core re-exports the safe Layer-3 vocabulary. Completion consumes the final
owner and performs its cleanup before returning success (or exclusive RX storage),
rather than exposing an additional `WireComplete` object requiring `finish()`.

| Operation | Required state | Hardware effect/evidence | Result |
| --- | --- | --- | --- |
| `start` | Idle | Write START into the freshly reset FIFO | StartQueued, or error |
| `transmit` | StartQueued | Configure/arm matching TX DMA; move the whole pair | Streaming, or error |
| `drain` | Streaming | DONE without DMA error, requests off, quiesce | TxDmaQuiescent, pending, or error |
| `stop` | TxDmaQuiescent | Check FIFO empty at point of use, enqueue STOP | Stopping, pending, or error |
| `complete` | Stopping | Observe STOP and controller idle; classify faults first; release owner | Success/payload, pending, or error |

The direct generator emits **register-state access restrictions**, including a Streaming
state that cannot write MTDR or reset MCR. The concrete paired lease restores
CPU access only after requests-off and quiescence. The PAC generator does not
know these protocol contracts. L2 owns ordered, consuming arm/shutdown, L3 owns named
START/STOP composition, and L4 owns fault priority; their reviewed behavior is
still needed in addition to register typing.

For another peripheral, reuse the pattern: specify an operation's required
state, effect, evidence, possible outcomes, and next state. Define that IP's
actual operations rather than forcing SPI or UART into an I2C START/STOP model.
Do not extract a bigger shared framework until a second small driver shows
which parts really repeat.

## What Rust prevents

These five mistakes were tested against the original PAC/Tock version.
The historical diagnostics below are recorded in VALIDATION.md; the current
direct safe-mmio map has additional diagnostic-matched compiler mutation cases.

| Mistake | Compiler result | Why it matters |
| --- | --- | --- |
| Write the read-only receive register | E0599: no `set` for `ReadOnly` | Direction is part of the register's type; the PAC enforces it too |
| Reach `self.0.hardware` from the transaction | E0616: private field | Driver code cannot bypass the vocabulary through that owner |
| Call `streaming.stop()` before draining DMA | E0599: no `stop` on `Streaming` | STOP is available only at the next state |
| Call `queued.stop()` twice | E0382: use of moved value | An operation consumes its old authority |
| Construct `StartQueued(())` outside the core | E0423: private fields | Only the protocol transition can mint that state |

The public API also has executable documentation checks: a second write through
the consumed driver and a stack-backed DMA source must fail compilation; the
matching single-write/static-source example must compile.

For a reader new to Rust:

- **Move:** ownership changes hands; the old variable cannot be used again.
- **Private field:** other modules cannot manufacture or inspect that value.
- **Type state:** `Streaming<B>` and `TxDmaQuiescent<B>` expose different methods.
- **Evidence:** an owned state returned only after the promised action, not a
  boolean the caller can invent or reuse for another channel.
- **Drop:** the owner runs cleanup when an ordinary scope, error, or cancellation
  releases it. The same hardware owner moves through all the states.
- **Static lifetime:** this storage stays valid for the entire program;
  exclusive RX ownership additionally prevents CPU reuse while DMA can write.

These rules apply to safe code using these boundaries. They are not proof that
the hardware implementation or transition specification is correct. A safe L3
mock can lie about protocol results, and an edit inside the trusted L2/HAL can
still encode the wrong physical behavior. Trusted dependencies may contain
unsafe code. The L3/L4 `forbid(unsafe_code)` rules are neither hardware
isolation nor runtime-correctness proofs. Compiler checks complement hardware
tests.

## Why this stays small

This extraction does not change the full production driver; earlier branch
work did. The opt-in one-shot controller reuses Embassy's singleton/pin/
clock support, eDMA HAL, executor, and timer. Its new nine-register map takes
offsets from the pinned PAC and state/access policy from an explicit manifest.
It does not call `controller::I2c` or its large protocol facade.
The three package boundaries now name L2's trusted capability, L3's safe
operations, and L4's protocol core; they are not additional runtime engines.
The old Abacus fork is no longer compiled; its source is temporarily retained
until the ported mutation suite is validated. The direct generator and its
tests remain real maintenance costs. The test hooks
do not replace the adapter's sequencing, WaitCell registration, or wake-only
ISR body.

The deliberately narrower contract is:

- One write or combined write/read per owner, 1..=32 bytes per phase,
  non-reserved 7-bit addresses.
- Static immutable source, exclusive static RX storage when receiving, and
  static peripheral ownership. RX storage is consumed on cancellation/error.
- Async + DMA only; fixed 100 kHz with a checked 12 MHz functional clock.
- One 100 ms software deadline across the entire transfer.
- Success, error, and cancellation all shut the local controller down.
- No reads, retries, repeated START, blocking mode, bus clear, or reconfiguration.
- No `embedded_hal_async::i2c::I2c` implementation: claiming that full trait
  while omitting its operations would misrepresent this example's scope.

Cleanup turns off interrupt/request generation, quiesces eDMA, then disables/
resets I2C and releases the pins. **It does not promise to recover a peer left
mid-transfer.** Reset both boards after an aborted run. A software timeout is
not a guarantee against broken DMA hardware: the shared HAL's ACTIVE-drain
assumes an in-flight memory transaction eventually finishes.

`mem::forget` does not run Drop. The static source and consumed static resource
tokens prevent this particular leak from becoming a dangling DMA buffer, but
it can leave hardware running. We do not call Rust's ownership model a proof
that every operation must eventually complete.

## Build and run

Requirements: the repository's Rust toolchain/ARM target, `flip-link`, and
`probe-rs`; two connected FRDM-MCXA577 boards. In
`examples/mcxa5xx`, build the two normal Embassy binaries:

If your local ignored Cargo.lock predates these optional dependencies, first
run the build once without `--locked` to resolve them; use locked builds for
subsequent validation.

```powershell
cargo build --locked --release --features i2c-one-shot --bin i2c-one-shot-controller --bin i2c-one-shot-target
probe-rs list
./one-shot/run-two-board.ps1 -ControllerProbe '1fc9:0143:YOUR_CONTROLLER_SERIAL' -TargetProbe '1fc9:0143:YOUR_TARGET_SERIAL'
```

Connect P3_20 to P3_20 (SDA), P3_21 to P3_21 (SCL), and GND to GND, with
pull-ups to 3.3 V. The runner flashes **both** selected boards. It starts the
target after the controller reaches its 10-second quiet startup window.
Slow startup fails the run; there are no hidden retries. Verdicts use RTT/
semihosting, so keep the probe sessions connected for this one-shot run.

Both must appear:

```text
ONE-SHOT CONTROLLER PASS: 16 bytes, DMA finished, STOP observed
ONE-SHOT TARGET PASS: exact 16 bytes and STOP
ONE-SHOT TWO-BOARD PASS
```

The target uses a 17-byte DMA receive buffer for the 16-byte message, ensuring
its result is the observed STOP, not just a full buffer. Each application is
small; the optional [cleanup check](checks/cleanup.rs) and
[validation record](VALIDATION.md) are separate from the example's normal path.

Host checks, from the repository root:

```powershell
cargo test --locked --manifest-path embassy-mcxa/Cargo.toml --no-default-features --features mcxa5xx,test,i2c-one-shot --lib
cargo test --locked --manifest-path embassy-mcxa/Cargo.toml --no-default-features --features mcxa5xx,one-shot-host-tests --lib
cargo test --locked --manifest-path embassy-mcxa/Cargo.toml --no-default-features --features mcxa5xx,test,i2c-one-shot --doc i2c::one_shot
cargo test --locked --manifest-path embassy-mcxa/experimental/i2c-one-shot-core/Cargo.toml
```

The separate [RX-service-withholding probe](RXSTALL.md) tests a resumable short
delay and the 100 ms timeout against a longer delay. Its electrical observation
availability is reported separately; a Timeout is not an SCL waveform verdict.
